# Agent Notes

Agent Notes 是由 agent 撰写的 RFC：持久的提案与决策记录，保留**理由、被放弃的备选方案、后果、以及需要哪些验证**。它不是任务清单，也不是变更日志 —— 变更日志在 commit 和 PR 里。

本文件定三件事：放哪里、什么时候写、写成什么样。

## 什么时候写一份

写：

- 选了一个结构性方案，且有别的方案被认真考虑过然后放弃。
- 引入或移除一条长期约束（门禁、行尾策略、目录边界、数据格式版本）。
- 一次"看起来可以更简单"的改动，需要挡住未来重复提出同一个简化。
- 迁移、格式变更、协议变更 —— 任何半年后有人会问"当初为什么这样"的事。

不写：

- 机械改动、局部改动、改名、格式修正。
- 单纯的功能实现（PR 描述足够）。
- 只在本地 UI 或文案层面的调整。

判断标准一句话：**这笔改动的理由能不能从代码和 PR 里读出来？** 读不出来才写。

## 目录状态

路径编码两个轴：`{状态}/{类别}/yyyy-mm-dd-<kebab-slug>.md`。

- **状态**是顶层目录，Note 的状态变了就移动文件：

| 目录 | 含义 |
|---|---|
| `proposed/` | 提议中，尚未落地。可以争论、可以否决。 |
| `implemented/` | 已落地。用**现在时**描述当前现实，不写"应该"、不写迁移计划、不写验收清单。 |
| `rejected/` | 认真考虑过但否决了。保留它，是为了不要有人第二次提同一个方案。 |
| `archived/` | 已被取代的冻结快照。 |

- **类别**是子目录，从下面这张关闭表里选。它不是自由主题名 —— 要开新类别就改这张表（以及将来的校验脚本），而不是在仓库里多一个目录。
- **日期**是这件事**第一次被提出**的日期（以 git 历史为准），不是最后修改日期。

| 类别 | 管什么 |
|---|---|
| `feature` | 面向用户或模型的新能力 |
| `bug-fix` | 修缺陷，或补 postmortem 指出的洞 |
| `simplification` | 删代码、删行为、删表面积，不加能力 |
| `architecture` | 关于**已发布源码**的结构决策：模块怎么摆、运行时词汇是什么 |
| `process` | 代码**周边**的工具与流程：门禁、依赖管理、构建 —— 不是运行时行为 |
| `testing` | 测试基础设施与策略 |

`architecture` 与 `process` 的分界：前者是我们发布的源码，后者是围着它的工具链。故意没有 `refactor` —— 它与 `simplification` 重叠，判别式「可观察行为变没变」已经覆盖。

不建 INDEX.md：路径本身就是索引，集中索引只会让无关的改动在同一条记录上打架。

## 文件格式

活动树里的每份 Note 用同一种格式。**格式目前靠评审守，本仓没有对应门禁** —— 要机械化就写 `scripts/check-notes.mjs`，判据就是下面这几条。

### 头部

前三行固定，第四行空行：

```markdown
# Agent Note: <标题>

Status: <状态>
```

`Status:` 只有三种写法，且必须与所在目录一致：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <一行理由>`

状态行里不放日期、不放括号补充：日期在文件名里，其余在 git 里。`rejected` 是唯一带内容的 —— 否决理由是读者来这条记录要找的那一句。

### 正文骨架

每份 Note 都以 `## Problem` 开头，写动机，要求脱离方案也能读懂。其后按状态分叉：固定章节用下面这些名字，不自创同义词；真正的专门章节（模块拓扑、协议契约、数据结构）可以夹在固定章节之间自由写。

`proposed/`：

```markdown
## Problem
## Proposal
…专门章节…
## Alternatives considered
## Acceptance criteria
## Risks
```

`## Proposal` 可以写将来时：计划、迁移步骤、未决问题都住这里。`## Acceptance criteria` 写"什么可观察状态算做完"，`## Risks` 同时写可能出什么错、以及这笔改动主动放弃了什么。

`implemented/`：

```markdown
## Problem
## Decision
…专门章节…
## Alternatives considered
## Consequences
```

`## Decision` 用现在时写已经落地的现实，并随代码一起更新。`## Consequences` 要写清这笔交易**花了什么、买到了什么**。提案期的标题在这里是错位的，不许出现：`## Proposal`、`## Plan`、`## Migration plan`、`## Acceptance criteria`。

`rejected/`：正文就是提案本身，保持它当时的章节（可以留 `## Acceptance criteria`、`## Plan`），结论写在 `Status:` 行。只强制要求头部、`## Problem`、`## Proposal` 与下面的备选方案一节。

### Alternatives considered 是必填

每份 Note 都要有 `## Alternatives considered`：逐个写清真正考虑过的方案、以及它为什么输了 —— 每个方案一段、加粗起头；争得凶的用 `### 为什么不是 X？`。

**没有备选方案的决策记录会招来第二次讨论**，而挡住重复讨论正是 Note 存在的理由。

备选方案是**记录**出来的，不是事后编的。当初确实没记的，写一行 `<!-- alternatives-not-recorded -->` 占位并说明原因 —— 假装备选方案比留白更糟。

## 在状态之间移动

移动目录 = 改 `Status:` 行 + 在同一次改动里重新满足目标目录的骨架：

- `proposed/` → `implemented/`：`## Proposal` 改写成现在时的 `## Decision`，`## Acceptance criteria` 与 `## Risks` 折进 `## Consequences`（或用现在时的 `## Testing` 写清楚现在靠什么钉住行为），删掉计划、只留实际发生的。
- `proposed/` → `rejected/`：只在 `Status:` 行加一句理由，正文冻结。
- 任何状态 → `archived/`：见下一节。

## 取代与归档

**每写一份新 Note 都要做一次取代检查**：在活动树里搜同一决策或同一机制的旧 Note，判断是否整体或部分取代。整体取代的，把旧的 `implemented/` 那份在**同一个 PR 里**移进 `archived/`；部分取代的保持活动状态，双向交叉链接。

整体取代时可以合并进当前拥有该决策的那份并删除旧的，前提是把旧记录里独有的理由、备选方案、后果、所需验证、已知覆盖缺口全部搬过去，并修好所有入站链接。**不能用 git 历史当作理由的唯一副本。**

`archived/` 下的文件是冻结的历史快照：**不要编辑、不要翻译、不要重排、不要移动，也不要当作当前权威**。需要推翻它，就写一份新的，链接过去。检索侧已用 [`.rgignore`](../../.rgignore) 把它排除在外。

## 写作要求

遵循 [文档标准](../../docs/AGENTS.md)。要点：

- 一段一行（编辑器软换行），不手动折行。
- 结论在前，理由在后，备选方案单列一节。
- 写清"被放弃了什么"，这是 Note 最有价值的部分 —— 只有结论的 Note 等于没有。
- 链接用仓库相对路径；历史引用用 tag 或 PR 号，不写 commit hash。
- 单篇上限 200 行（见[预算](../../docs/AGENTS.md#预算)）。超了先想是不是该拆成两份，而不是提上限。
