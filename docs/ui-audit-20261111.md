## 附录 F · B1 硬编码颜色映射表与迁移结论（第 28 轮）

### 扫描
`styles.css` + `styles-2.css` 共 1443 处颜色字面量；与主题 token **数值相等**的高频项：

| 次数 | 字面量 | 数值相等的 token | 迁移风险 |
|---|---|---|---|
| 103 | `#37352f` | `--accent`（亮色） | **高**：多用作正文色，语义与 accent 不同 |
| 38 | `#787774` | `--muted`（亮色） | 中：多数确实是次要文字 |
| 25 | `#ececea` | `--border`（亮色） | 中：部分用作背景 |
| 24 | `#e9e9e7` | `--border`（亮色） | 中 |
| 14 | `#f7f7f5` | `--surface-2/-bubble-ai` | 低（背景） |

| 12 | `#fbfbfa` | `--surface-3` | 低 |
| 12 | `#d9a868` | `--accent`（烛光） | **高**：多为主题专属强调，已 scoped |
| 9 | `#ffffff` | `--bg/-input-bg` | **高**：不能全局替换 |
| 6 | `rgba(217,168,104,.18)` | `--border`（烛光） | 低 |

### 结论：不做全局替换
数值相等 ≠ 语义相等。`#37352f` 在亮色里既当正文又当 accent，`#ffffff` 既当底色又当输入框底——
全局替换会在其它主题下产生连锁变色（本仓库四主题各有 2-ID 覆盖层，正是过去这种替换的产物）。

**B1 的正确做法（建议白天按此推进）**：
1. 以组件为单位（卡片/行/按钮/输入框），一次一个，改完截四主题对比图；
2. 只替换「在该主题规则内、语义明确」的字面量（例如亮色 scope 里的 `#ececea` → `var(--border)`）；
3. 每批跑 `check-syntax` + 四主题截图，出现任何色差立即回滚该批。

今晚已完成的是 B4 相关的三组 token（`--danger*` / `--ctl-*` / `--empty-*`），它们覆盖了最常被复制的
危险色与控件几何；剩余 1400+ 处按上述组件化流程白天推进，不在夜间批量冒险。

### 抽取方案 `public/shared/chat-stream.js`
```js
window.__chatStream = {
  modeForModel(model),   // APP_MODELS_FAST 判档（coding/flow 现有逻辑）
  call(opts)             // { profile:'rp'|'assist', system, user|messages, model, signal, onDelta, unlock?:true }
```

内部统一：body 组装、unlockToken/baseId/neutralId、fetch、SSE 解析（含 `[DONE]`/注释行）、abort。

### 迁移顺序（每页一次真窗回归）
1. studio + write：函数体换成 `return __chatStream.call({profile:'rp',...})`，行为应完全等价
2. coding：去掉本地 `aiModeForModel` 与 reader，改 `profile:'assist'`，保留内部 AbortController
3. flow：同 coding，但**行为变化点**：会开始发 unlockToken/baseId/neutralId（与其他三页一致）——需确认这是期望行为后再合

### 风险
- flow 无 abort，迁移后若传 signal 会新增取消能力（低风险）
- 四页都在 `/api/chat` 契约上，服务端字段不变；抽取只动前端
